# Procedural 10M / 100M lifecycle and scaling fixture

This opt-in fixture streams actual deterministic Gaussian payloads through the
ordinary package renderer. Every source record belongs to a real leaf range;
10M uses 2,442 leaf pages and 100M uses 24,415, with 4,096 records per page and
an exact partial final leaf. The hierarchy has distinct world-space bounds for
every city block. Requested leaves are generated by `VirtualCityScene`, including
their positions, rotations, scales, opacity, and SH coefficients.

Internal representatives and ABI-16 correspondence are synthetic lifecycle
fixtures. They have **no fitted image-quality or error-certificate qualification**.
The source hash in capture records identifies the generator code and parameters,
not a materialized source asset. This distinction is recorded in instrumentation.

## Separate preparation from GPU measurements

Build once using the same native feature profile as the other LoD captures:

```sh
CARGO_BUILD_JOBS=2 cargo build --locked --release --bin capture_lod_virtual_city --no-default-features --features 'planar lod_render sh3 io_flexbuffers headless testing'
```

These commands perform an explicit CPU-only prehash pass. They never open a GPU.
They generate and discard one page at a time, write only the validated manifest
and preparation metadata, and refuse to overwrite an earlier preparation.

```sh
target/release/capture_lod_virtual_city prepare --config tools/fixtures/lod_virtual_city_10m.json
target/release/capture_lod_virtual_city prepare --config tools/fixtures/lod_virtual_city_100m.json
```

Prehash requires **O(source records) CPU work**. There is no zero-hash shortcut,
placeholder page, or 24GiB payload archive. `preparation.json` records elapsed
prehash time, manifest bytes, exact source/leaf counts, generator and executable
identity, and before/after RSS (not peak RSS). Metadata is O(page count), with
at most 32,768 leaves and two hierarchy nodes per leaf. Preparation is sequential
and does not silently consume another CPU worker budget.

The following commands open a real GPU. Run them only in a coordinated GPU slot:

```sh
BEVY_ASSET_ROOT="$PWD" target/release/capture_lod_virtual_city run --config tools/fixtures/lod_virtual_city_10m.json
BEVY_ASSET_ROOT="$PWD" target/release/capture_lod_virtual_city run --config tools/fixtures/lod_virtual_city_100m.json
python3 tools/check_lod_virtual_city.py target/lod-roadmap/virtual-city/10m-capture target/lod-roadmap/virtual-city/100m-capture
```

Both runs share a fixed viewport, camera route, near/far planes, active/resident
budgets, seed, and block grid. The source grows beyond the visited route. Each
run includes cold load, stationary draw, 768-world-unit movement, rapid return,
another eviction traversal, unload to a zero scene ledger, and reload. Phase
progression requires an actual nonzero same-submission indirect readback plus
draw-command attestation. Slot/page generation changes are counted before
unload, and at least two actual leaf payloads must appear in rendered candidates.
The full lifecycle must finish within the configured timeout (default 300s).

The lazy server has exactly two handler threads, an 8KiB HTTP header limit,
five-second socket deadlines, no payload cache, and no userspace request queue.
It regenerates and validates requested bytes against immutable page hashes;
responses have exact length/range headers and SHA-256 ETags. Its procedural CPU
generation cost is included in runtime observations. Loopback results qualify
neither remote network behavior nor disk/CDN/cache deployment.

`capture.jsonl` and `submission_evidence.jsonl` reuse the native asynchronous
readback harness, including its finite three-slot ring and actual submitted
generation proofs. `lifecycle.jsonl` records sampled RSS, the shared scene memory
ledger, package/request gauges, and physical slot/page generations. `status.json`
contains phase, retirement, page-generation, and handler evidence. Optional
images use the same production target. No software adapter is accepted.

Fixture metadata/server storage and capture staging are outside the scene ledger
and remain visible in process RSS. Zero ledger on unload proves scene reservation
retirement, not return of process RSS or destruction of the cached manifest asset.
Reload intentionally retains that asset. RSS is sampled, not a device-memory
measurement. Timing is instrumented and includes lazy generation/readback work.

The checker refuses a source-size comparison if actual settled stationary/reload
draw work differs by more than 1% (explicitly configurable), or if the camera or
budgets differ. It reports measured draw and frame-wall medians without inventing
a performance pass threshold. Passing this fixture remains diagnostic lifecycle
and scaling evidence; `release_qualified` is always false.

Lightweight checks, without opening a GPU:

```sh
python3 -m unittest discover -s tools -p test_lod_virtual_city.py
```

Three Rust CPU tests exercise real leaf coverage and payload hashes, bounded
configuration, and regenerated loopback range bytes. They are part of the normal
headless/testing library test build; the CLI is the only GPU entrypoint.
